# IrisPipe 下一階段實作計畫

## 文件目的

本文件是 IrisPipe 下一階段的實作設計稿，目的不是直接討論 Spring Batch restart 細節，而是先重新對齊產品邊界：

- IrisPipe 對外的執行單位應該是 `pipeline`
- `job` / `jobExecution` / `stepExecution` 是內部 runtime 邊界
- 後續的 retry、resume、restart 都應該建立在 `pipeline run` 之上

本文件取代先前以 `job restart API` 為中心的切入方式，改成 `pipeline-run first`。

## 核心前提

以下結論視為本階段已拍板：

1. IrisPipe 的對外執行邊界是 `pipeline`，不是 `job`
2. Spring Batch 的 `job` 仍然是內部實作邊界，不直接作為公開 API 主語
3. `atomicLevel = JOB` 與 `atomicLevel = CHUNK` 的差別，應該被視為「pipeline 內某個 job 的恢復策略差異」
4. 第一版先採 `sequence-first`，不先做完整 DAG 編排
5. restart 分階段處理：
   - 先做 `JOB` 型 job 在 pipeline 中的斷點續傳
   - 再做 `CHUNK` 型 job 在 pipeline 中的斷點續傳
   - 最後自然支援 mixed pipeline

## 本階段總目標

本階段只做三件事：

1. 將公開 execution API 升級為 pipeline-level API
2. 新增 `pipeline run` runtime persistence
3. 用 K6 保護新的 pipeline-level API 與既有 runtime 行為

本階段刻意不先做 restart / resume 實作本身，但資料模型必須為後續 resume/restart 保留正確邊界。

## 目前系統基線

### 設定模型

- `sync-config` 已經是 pipeline 為單位的設定管理 API
- `pipeline` 會持久化於：
  - `iris_pipeline`
  - `iris_pipeline_job`
  - `iris_pipeline_job_connection`
  - `iris_pipeline_execution`
  - `iris_pipeline_execution_parameter`
- runtime 執行時會依 `pipelineId` 重建 `List<SyncJobDefinition>`

### 目前執行模型

- 目前執行入口雖然是 `pipelineId`，但公開 API 與 metadata 仍偏向 `job` 層級
- `atomicLevel` 已在 runtime 生效：
  - `JOB`：outer job transaction
  - `CHUNK`：依 Spring Batch chunk commit 執行
- watermark 仍維持 whole-job success 才寫入

### 目前缺口

- 缺少 `pipeline run` 這一層
- 對外查詢、明細、刪除仍以 `job` 為主語
- 尚未有 resume / restart 所需的 runtime identity

## 新的 runtime 模型

### 1. `Pipeline`

`Pipeline` 是靜態配置單位，也是對外 trigger 的輸入單位。

### 2. `PipelineRun`

`PipelineRun` 是一次 pipeline trigger 後的 runtime 實體，是未來 query/detail/delete/retry 的對外主語。

它代表：

- 哪個 pipeline 被執行
- 何時被觸發
- 整體執行是否成功
- 目前跑到哪一個 job

### 3. `PipelineRunJob`

`PipelineRunJob` 是 `PipelineRun` 內部的 job 節點紀錄。

第一版採 sequence-first，所以它只需要表示 pipeline 中按順序執行的 job 節點，不先做 graph edge table。

每個 `PipelineRunJob` 至少要記錄：

- `pipeline_run_id`
- `job_sequence_order`
- `job_name`
- `atomic_level`
- `status`
- `root_job_instance_id`
- `last_job_execution_id`

### 4. `root_job_instance_id` 與 `last_job_execution_id`

這兩個欄位是後續 resume/restart 的必要 runtime identity：

- `root_job_instance_id`
  - 代表該 pipeline 節點第一次掛上的 Spring Batch job instance lineage
- `last_job_execution_id`
  - 代表該節點目前最後一次 execution 的落點
  - 後續 resume 時，主要會從這個 execution 往回找狀態與 metadata

目前雖然還不做 restart，但這兩個欄位本期就要建立並寫入。

## 公開 API 邊界

本階段將 execution API 全部升級為 pipeline-level：

- `POST /api/v1/sync-pipeline`
- `GET /api/v1/sync-pipeline?ids=...`
- `GET /api/v1/sync-pipeline/{pipelineRunId}`
- `DELETE /api/v1/sync-pipeline/{pipelineRunId}`

### API 語意

- trigger：建立一個新的 `PipelineRun`
- query：查詢一批 `PipelineRun` summary
- detail：查詢單一 `PipelineRun` 與其底下 `PipelineRunJob`
- delete：刪除該 `PipelineRun` 相關 runtime metadata

### 本期支援範圍

本期支援同步與非同步兩種 pipeline trigger，但兩者共用同一套 sequence-first orchestration 與 runtime lifecycle。

- `useAsyncLaucher = false`
  - API 會等待整條 pipeline 跑完，再回傳 terminal summary
- `useAsyncLaucher = true`
  - API 會先建立 `PipelineRun` / `PipelineRunJob`，提交背景執行後立即回傳 summary
- 無論同步或非同步 trigger
  - pipeline 內 job 仍依 `sequence_order` 逐一執行
  - `PipelineExecutionService` 只負責建立 `PipelineRun`、建立初始 `PipelineRunJob`、啟動整條 pipeline
  - `CustomJobListener` 透過 `PipelineRunLifecycleService` 回寫 `PipelineRun` / `PipelineRunJob` 狀態

## 建議資料表草案

### `iris_pipeline_run`

```sql
CREATE TABLE iris_pipeline_run (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    pipeline_id BIGINT NOT NULL,
    requested_async BOOLEAN NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    start_time TIMESTAMP NOT NULL,
    end_time TIMESTAMP,
    updated_at TIMESTAMP NOT NULL,
    CONSTRAINT fk_iris_pipeline_run_pipeline
        FOREIGN KEY (pipeline_id) REFERENCES iris_pipeline(id)
);

CREATE INDEX idx_iris_pipeline_run_pipeline_id
    ON iris_pipeline_run (pipeline_id);
```

### `iris_pipeline_run_job`

```sql
CREATE TABLE iris_pipeline_run_job (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    pipeline_run_id BIGINT NOT NULL,
    job_sequence_order INT NOT NULL,
    job_name VARCHAR(255) NOT NULL,
    atomic_level VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL,
    root_job_instance_id BIGINT,
    last_job_execution_id BIGINT,
    created_at TIMESTAMP NOT NULL,
    start_time TIMESTAMP,
    end_time TIMESTAMP,
    updated_at TIMESTAMP NOT NULL,
    CONSTRAINT fk_iris_pipeline_run_job_run
        FOREIGN KEY (pipeline_run_id) REFERENCES iris_pipeline_run(id),
    CONSTRAINT uk_iris_pipeline_run_job_order UNIQUE (pipeline_run_id, job_sequence_order)
);

CREATE INDEX idx_iris_pipeline_run_job_run_id
    ON iris_pipeline_run_job (pipeline_run_id);

CREATE INDEX idx_iris_pipeline_run_job_last_execution_id
    ON iris_pipeline_run_job (last_job_execution_id);
```

## 執行流程

### trigger

```text
POST /api/v1/sync-pipeline
    |
    v
validate pipeline exists
    |
    v
create iris_pipeline_run(status = STARTING)
    |
    v
load jobs from persisted pipeline ordered by sequence
    |
    v
create all iris_pipeline_run_job(status = PENDING)
    |
    +--> if useAsyncLaucher = true
    |       submit sequence-first pipeline execution to TaskExecutor
    |       return pipeline run summary immediately
    |
    +--> if useAsyncLaucher = false
            continue in current thread
    |
    v
for each job
    |
    +--> build SyncJobContext
    |
    +--> create Spring Batch Job
    |
    +--> jobLauncher.run(job, identifying params)
    |
    +--> CustomJobListener.beforeJob(...)
    |       -> PipelineRunLifecycleService.markJobStarted(...)
    |
    +--> CustomJobListener.afterJob(...)
    |       -> PipelineRunLifecycleService.markJobFinished(...)
    |
    +--> if job failed
            stop pipeline execution
            return pipeline run summary
    |
    v
all jobs completed
```

### query / detail

`PipelineRun` summary 與 detail 都應直接讀 `iris_pipeline_run` / `iris_pipeline_run_job`，必要時再補查 Spring Batch metadata 作為輔助資訊。

### delete

刪除 `PipelineRun` 時：

1. 讀出其底下所有 `PipelineRunJob`
2. 對每個有 `last_job_execution_id` 的節點，嘗試刪除對應 Spring Batch metadata
3. 刪除 `iris_pipeline_run_job`
4. 刪除 `iris_pipeline_run`

對外刪除的單位仍然是 pipeline run，不是單一 job metadata。

## 後續 resume / restart 分階段方向

### Phase A：`JOB` 型 job 的 pipeline resume

先不做 Spring Batch restart，而是做 pipeline 層級的斷點續傳：

- 找到第一個 failed `PipelineRunJob`
- 前面已完成的 job 跳過
- 從該 failed job 重新 replay 整個 job

這是 `atomicLevel = JOB` 的恢復模型。

### Phase B：`CHUNK` 型 job 的 pipeline resume

當 `PipelineRunJob` 是 `atomicLevel = CHUNK` 時：

- 仍然從 pipeline 的 failed job 節點切入
- 但節點內部不是 replay job
- 而是依 snapshot + Spring Batch metadata 做真正 restart

### Phase C：mixed pipeline

當 pipeline 同時包含 `JOB` 與 `CHUNK` 型 job：

- pipeline 仍然只找「下一個應接續的 failed job」
- 該 job 要 `replay` 還是 `restart`，由該節點的 `atomicLevel` 與 snapshot 決定

## 本階段建議實作順序

### Step 1. 先改公開 API 邊界

- 新增 `SyncPipelineAPI`
- 將 trigger / query / detail / delete 全部升到 pipeline-level
- 舊的 job-level execution API 不再作為對外主語

### Step 2. 新增 runtime tables 與 persistence

- migration：`iris_pipeline_run`
- migration：`iris_pipeline_run_job`
- entity / repo / service 寫入與查詢

### Step 3. 改 execution orchestration

- pipeline execution 失敗時要停止後續 job
- 執行過程中寫入 `PipelineRun` / `PipelineRunJob`
- 寫入 `root_job_instance_id` / `last_job_execution_id`

### Step 4. 補 K6 保護層

既有 runtime regression 仍需保留，但入口改為新的 pipeline-level API。

至少要覆蓋：

- pipeline trigger 成功
- pipeline summary 查詢
- pipeline detail 查詢
- pipeline delete 成功
- `JOB` / `CHUNK` runtime 差異仍持續成立

- 公開 execution API 已完全升到 pipeline-level
- `PipelineRun` / `PipelineRunJob` 已落地

  - 本期先做 pipeline-run
  - 下一期先做 `JOB` pipeline resume
  - 再下一期做 `CHUNK` pipeline resume
